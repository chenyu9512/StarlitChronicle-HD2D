# 《星灯纪行》批次开发与一次验收规则

生效对象：`main` 为发行基线；`fix/*`、`dev/*`、`feature/*` 为有限生命周期开发分支。**本政策必须在 PR 合并进入 main 后，才能视作主分支正式生效。**

## 原则
- **小改动连续提交，不逐次运行重型 CI**。一个批次围绕相同玩法/场景/工程目标集中开发，结束时一次性进行完整测试。参考批次为约 **2–4 周或一个可验收的玩法子系统/第1–3章黄金样板**，不用固定按提交次数触发。
- 仓库12条工作流不再由 `push` 自动触发；非核心专项均可在 Actions 里手动 `Run workflow`。
- 唯一自动的完整质量门槛是 `Godot 4.7.2 Core Validation`：将当前**同仓库**开发 PR 从 **Draft → Ready for review** 时启动一次。此阶段应该已经完成本批全部修改。
- 任何人工需要复测时，先把 PR 设回 Draft，再转 Ready，确保最后一次测试与最新提交一致。手动 `workflow_dispatch` 只运行测试，不自动合并。合并期间再提交会触发 SHA 防护而拒绝旧测试合并。
- 自动合并仅针对同仓库开发 PR、目标 `main`、分支名为 `fix/*`、`dev/*`、`feature/*` 且不是历史 `feature/content-foundation-v0-2`。历史 `content/full-story-v1` 也不在管理范围。
- 完整 Core Validation **所有步骤成功**后，独立的最小授权 job 检查 PR head SHA 与测试时一致，并要求 `main` 未在测试期间更新，然后通过 GitHub API **Squash merge → 删除已合并的精确开发分支**。
- 若测试失败、Runner未分配、分支中途更新、主分支变化、权限不足或分支保护拒绝合并，**不合并、不删分支**；在同一开发分支修复，完成整个批次后重新触发验收。
- 严禁通过脚本强推 `main`、忽略失败测试或删除未经审核的历史开发分支。禁止自动合并来自 fork 的 PR。所有实际发布和 iPhone 真机测试仍需另行验收。

## 一个开发批次的操作
1. 从最新 `main` 建立 `dev/<milestone>` 或 `fix/<scope>`，创建 Draft PR。
2. 连续提交本批小改动；期间不触发重型 Actions。开发者可做必要的局部人工检查，但不要把静态分析视为运行时认证。
3. 完成代码/素材/任务/玩法制作后，在 PR 里写明范围、测试重点、旧存档兼容和风险，再点击 **Ready for review**。
4. 质量门槛在 GitHub Actions 运行：包含脚本导入、战斗、剧情、地图、存档、内容和美术静态/运行时验收。
5. 全绿且代码/主分支 SHA 未变 → 工作流自动 squash 合并、删除开发分支。否则继续保持 PR 待修。
6. 合并后 **不额外自动运行全部专项 CI**；需要桌面包、艺术截图或设备验证时，再手动启动对应工作流。

## GitHub Actions 阻断
截至2026-10-26，仓库的最新工作流曾出现 `runner_id=0`、`steps=0` 的作业分配失败；此时 CI **并未运行**。本政策不会绕过 Runner 问题，也不会把这种失败判为 PASS。先解决 Issue #4 才能可靠自动合并。

## 近期开发排程建议
- 批次 A（P0）：V3存档恢复、新游戏→第三章真实战斗、卡关处理、地图切换及回归。
- 批次 B（P1）：晨露村/白砂港/断桅海蚀洞可玩场景、三种不同普通怪、一场精制 Boss、一个带回访的分支选择。
- 批次 C（P1）：第一幕第4–6章补完、战斗数值与触控 UX、家园/经济兼容及游戏时长测试。

**说明：** 专项工作流暂时只可手动触发。Core 测试的自动合并只能覆盖其自身测试所实际检查的项目，不代表 App Store 准入、商业美术终审或所有设备质量测试已经通过。
